========================================
TICKET REW-10: RECIPE SEARCH
IMPLEMENTATION SUMMARY
========================================

OVERVIEW
--------
Added public search across all published recipes, available whether or not the
visitor is logged in. Includes a Postgres full-text search index with relevance
ranking, a paginated browse page, and a read-only public recipe page so search
results are reachable without an account.


========================================
FEATURES IMPLEMENTED
========================================

1. PUBLIC RECIPE SEARCH
-----------------------

User Stories Completed:
- Search published recipes while logged out
- Search published recipes while logged in
- Results ranked by relevance, not just recency
- Partial word matching (typing "chick" finds "Chicken")
- Paginated results (12 per page)

Search Coverage (in weight order):
- Title (weight A - highest)
- Author (weight B)
- Ingredients (weight C)
- Notes (weight D - lowest)

Query Syntax Supported (via websearch_to_tsquery):
- Plain terms: chicken pasta
- Quoted phrases: "olive oil"
- Exclusions: pasta -tomato
- OR terms: chicken or beef


2. PUBLIC BROWSE PAGE
---------------------

- Lists every published recipe, newest first
- Paginated, 12 per page
- Reachable logged out
- Empty state adapts based on login status


3. PUBLIC RECIPE VIEW
---------------------

- Read-only recipe page at /r/:id
- Serves published recipes only; drafts return 404
- Hides Edit and Delete controls from non-owners
- Shows an Edit link when the viewer owns the recipe
- Shows a sign-up call to action for logged-out visitors


4. USER INTERFACE
-----------------

- Search box added to the navbar on every page
- Search bar added to the home page hero
- "Browse" link added to the navbar for all visitors
- Existing "Recipes" nav link relabelled "My Recipes" to distinguish the
  private area from public browse
- Shared recipe card and pagination partials to avoid duplicated markup
- Responsive: search box moves to its own row on screens under 768px


========================================
ROUTES ADDED
========================================

GET /search          Public. Ranked search results. Empty query renders a
                     prompt state rather than listing everything.
GET /browse          Public. All published recipes, newest first, paginated.
GET /r/:id           Public. Read-only view of a single published recipe.

Existing routes were not changed. /recipes and /recipes/:id remain behind
requireAuth and continue to serve the private "my recipes" area.


========================================
DATABASE CHANGES
========================================

Migration: database/migrations/003_add_recipe_search.sql

Schema Updates:
- Added generated column recipes.search_vector (tsvector, STORED), built from
  title, author, ingredients and notes with setweight() applied per field
- Generated column means the index stays current automatically; no trigger and
  no application code needed to maintain it

Indexes Added:
- idx_recipes_search_vector    GIN index on search_vector
- idx_recipes_published_created  Partial index on created_at DESC WHERE
                                 status = 'published', covering the browse page
- idx_recipes_title_trgm       GIN trigram index on title (optional, speeds up
                               the partial-word ILIKE fallback)

Function Added:
- public.search_recipes(search_query text, result_limit int, result_offset int)
  Returns ranked published recipes plus a total_count window column, so
  pagination needs only one round trip instead of a separate count query.
  Declared STABLE and SECURITY INVOKER.
  EXECUTE granted to anon and authenticated.


========================================
SECURITY AND ACCESS CONTROL
========================================

NO RLS POLICY CHANGES WERE REQUIRED.

The existing policy from migration 001 already permits this:

  CREATE POLICY "Users can view published recipes"
    ON recipes FOR SELECT USING (status = 'published');

It has no TO clause, so it applies to PUBLIC, which includes the anon role.
Anonymous reads of published recipes were already allowed by design.

Defence in depth applied:
- search_recipes() is SECURITY INVOKER, so RLS is enforced for the calling
  role rather than the function owner. A definer-rights function here would
  have bypassed RLS entirely.
- Every public query also filters status = 'published' explicitly in
  application code, independent of RLS.
- Public routes deliberately use the anon-key client rather than the user's
  access token, so results are identical logged in or out and a session can
  never widen what search returns.
- Search input is passed as a bound RPC parameter. No string interpolation
  into a PostgREST filter expression, which avoids the .or() filter injection
  class of bug.
- LIKE metacharacters (%, _, backslash) in user input are escaped in SQL so a
  literal % in a query stays literal instead of acting as a wildcard.
- Query length capped at 100 characters; result_limit clamped to 50 server side.
- :id is validated against a UUID pattern before querying, since Postgres
  errors on a malformed uuid cast.
- Drafts and non-existent recipes both return an identical 404, so the
  response does not reveal whether a draft exists.

Existing general rate limiting (100 requests / 15 min / IP) applies to the new
routes automatically.

========================================
KNOWN ISSUES AND FOLLOW-UPS
========================================

1. .env.example was deleted in commit ab60f31 (12 lines removed). This appears
   accidental rather than intentional. It is a tracked file other developers
   need for setup, and the README still instructs them to copy it. Recommend
   restoring it in a follow-up commit:
     git checkout cb81222 -- .env.example

2. CSRF protection remains disabled in src/app.js from the REW-9 work, with a
   TODO to re-enable it. Out of scope for this ticket, but it is still off.
   The routes added here are all GET and carry no state change, so they do not
   widen that exposure.

3. package.json declares engines node >=18, but file-type@22 and
   supabase-js@2.110 both require Node 22 and sharp requires 20.9+. The
   declared range is wrong and lets an unsupported Node version install
   cleanly, then fail at runtime. Not caused by this ticket, but worth a
   follow-up.

4. Search relevance uses the 'english' text search configuration. Recipes
   written in other languages will stem poorly. Acceptable for now.

5. No search result highlighting or snippets. Could be added later with
   ts_headline().
