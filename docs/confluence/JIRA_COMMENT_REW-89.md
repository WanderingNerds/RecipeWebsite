# Jira Comment for REW-89 Documentation

REW-89 standardizes the recipe cards inside a meal plan, completing the card-standardization series across all five authenticated surfaces. Every card on `/meal-plans/:id` now shows a clickable title, the favorite heart, author and `Adapted from` attribution, category and tag chips, `Prep Time:` / `Cook Time:` / `Servings:` / `Difficulty:`, plus `+ Cookbook`, Share, Remove, and owner-only Edit and Delete. `+ Meal Plan` is deliberately absent — the recipe is already in a meal plan. Browse, My Recipes, My Favorites and Cookbook are unchanged, as is the grocery-list flow and every piece of page furniture on the plan page.

This is not a new card. The shared partial `views/partials/recipe-summary-card.ejs` gained a fifth `surface` value, `'meal-plan'`, and exactly **two** flag changes: a new `showMealPlanAdd = !isMealPlan` (which is what implements "do not display + Meal Plan", and is `true` on all four pre-existing surfaces so none of them changed), and `showStatusPill` extended with `|| (isMealPlan && isOwner)`. The heart, `+ Cookbook`, owner-gated Edit/Delete, `Adapted from`, plain-text chips and the `/recipes/:id` title link all came free from flags that already existed. A new optional `mealPlanId` local lets the partial render this page's Remove form — absent it, no Remove button is drawn rather than a broken URL. The cookbook and meal-plan action rows were deliberately **not** merged into one parameterized branch: they differ in the suppressed add-button, the Remove URL, the confirm copy and the absence of `returnTo`, and merging them would risk regressing REW-88.

**This is the first genuinely mixed-ownership card surface.** Migration 012's RLS INSERT policy on `meal_plan_recipes` admits your own recipes *or* anyone's published recipe, so a card you do not own is a normal production case here. Edit/Delete owner-gating is therefore a live protection rather than future-proofing, and the Private/Public pill is now shown **only to the recipe's owner** — the old page showed one on every card, including other people's recipes. That pill is a deliberate deviation from the ticket's requirement list, carried over from REW-88 (it is how an owner learns a Private recipe will not appear to people they share the plan with, per REW-69), and it still wants explicit product sign-off.

On the route side, `getMealPlanRecipes` was widened to `MEAL_PLAN_CARD_COLUMNS` (`user_id`, `original_author`, and embedded `recipe_categories` / `recipe_tags` flattened into `categories` / `tags`) and exported, and `GET /meal-plans/:id` was extracted into an exported `handleMealPlanView(req, res, { createClient } = {})` that stamps `isLiked` from one batched `recipe_likes` query scoped to the caller — none at all for an empty plan, and a likes error logs and renders hearts unfavorited rather than failing the page. One plan read, one recipe read, one likes read regardless of plan size. The grocery-list query `getMealPlanRecipeIngredients()` was deliberately left narrow and untouched. No new endpoint, no new rate limiter, and no change to helmet, CORS, `csrf-csrf`, `express-rate-limit` or the auth middleware; `GET /meal-plans/:id` still runs behind `requireAuth` after the extraction, and `POST /meal-plans/:id/recipes/:recipeId/remove` keeps every guard it had.

**No database migration** — 020 remains the highest applied migration. Every column the widened select adds is already readable under applied policies 001, 018, 005/006 and 013, and `recipe_likes` is read on the request-scoped, RLS-scoped client with an explicit `user_id` filter on top. No new environment variable, package, CSS, client-side JavaScript, or Vercel configuration change.

Review is **approved on round 1 with no blocking issues**. `npm test` reports **526 tests, 524 passing, 2 failing**; both failures are pre-existing environmental unix-socket errors in `src/csrf.integration.test.js` on Windows (`listen EACCES` on `/tmp/*.sock`), a file untouched by this diff and already failing on `main`, tracked as REW-98. No new failures.

**The QA stage was deliberately excluded from this automated run.** The pipeline was Planner → Developer → Reviewer → Documentation, with no QA stage at all. The reviewer ran the full suite, but **no dedicated QA pass against the acceptance criteria was performed, and the browser/manual verification described in the plan has not been done**: a plan containing your own Public recipe, your own Private recipe and another user's Public recipe (the mixed-ownership case this surface makes real); desktop and mobile widths with the five-control action row wrapping rather than overflowing; the heart toggling and persisting across a reload; `+ Cookbook` actually adding; Remove leaving the recipe intact; Delete confirming first; keyboard reachability and focus visibility. **This change should not be described as QA-verified.** The change is also uncommitted. Status stays **In Progress**.

Known, intentional scope boundary: the public shared meal plan view `/m/:id` was left unchanged. It still renders the older `views/partials/recipe-card.ejs` and still shows a `+ Meal Plan` button, which the owner view no longer does. REW-88 drew the same line at the public cookbook view.

Three non-blocking reviewer items were recorded and deliberately not actioned in this ticket: (1) `MEAL_PLAN_CARD_COLUMNS`, the categories/tags flatten and the batched-likes block are now triplicated across `mealPlanRoutes.js`, `cookbookRoutes.js` and `index.js` — suggested extraction is a new `src/utils/recipeCardQuery.js` exporting `RECIPE_CARD_COLUMNS`, `flattenRecipeCardRows()` and `stampLikeStatus()`; (2) two loop entries in `src/views/recipeVisibility.test.js` (meal-plans, and cookbooks since REW-88) are now vacuous for their stated purpose, since they assert against template source for pills that have moved into the shared partial — suggested fix is to add the partial to that test's file loop; (3) the `/m/:id` vs `/meal-plans/:id` `+ Meal Plan` inconsistency needs a Product decision.
