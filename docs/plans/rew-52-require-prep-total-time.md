## Summary
QA found that the "New Recipe" and "Edit Recipe" forms allow saving a recipe with Prep Time and/or Cook Time left blank. This plan adds required-field enforcement — visible `*` markers, inline "Required" error messages with a red border/label on blank submission, live-clearing of the error once a value is entered, and a matching server-side guard — to both time fields on both forms, without introducing a database migration. Investigation found the codebase has no `total_time` concept anywhere (schema, routes, or views) — only `prep_time` and `cook_time` exist end-to-end (the OCR importer parses a `totalTime` value but it is discarded and never persisted or displayed, confirming it isn't a real feature today). The plan therefore treats the ticket's "Total Time" as the existing "Cook Time" field, relabeled — see Open Questions for the full rationale and the alternative if that assumption is wrong.

## Open questions / assumptions
- **"Total Time" does not exist in the app today — biggest open question.** `database/schema.sql` / `database/migrations/001_create_recipes_table.sql` / `database/README.md` define only `prep_time` and `cook_time` (both nullable `TEXT`). The create/edit forms (`views/recipes/new.ejs`, `views/recipes/edit.ejs`) only ever collect "Prep time" and "Cook time." `src/utils/recipeImporter.js` does parse a `totalTime` value out of OCR/PDF text (`extractRecipeMetadata`), but it is never included in the object returned to the UI (only `prepTime`/`cookTime` are), never rendered in `views/recipes/import.ejs`, and never saved by `POST /recipes/import/save` — it's dead data today. Given this, I'm **assuming the ticket's "Total Time" field is meant to be the existing "Cook Time" field, relabeled** in the UI to "Total Time" (task list below implements this: change the visible label text only, keep `name="cookTime"`/`cook_time` unchanged to avoid a schema migration and avoid rewriting every place `cook_time` is read: `views/recipes/view.ejs`, `views/recipes/public-view.ejs`, `views/partials/recipe-card.ejs`, `src/routes/importRoutes.js`, `database/migrations/003_add_recipe_search.sql`'s search vector). **If this assumption is wrong** — i.e., product actually wants a true third concept, prep + cook ≠ total, entered independently — this becomes a materially bigger ticket: new `total_time` column (migration), new form field, new required check, and updates to every read site listed above. Recommend the Developer confirm this reading with the reporter/PM before starting; flagging loudly rather than silently guessing given the schema mismatch is a genuine product-data question, not just an implementation detail.
- **Scope: manual create/edit only, not Import.** The ticket's QA finding language ("a recipe can be saved without…") most naturally targets the primary Add/Edit Recipe form, and the task prompt explicitly frames it as "likely the recipe create/edit form." `views/recipes/import.ejs` / `POST /recipes/import/save` (`src/routes/importRoutes.js`) are a separate flow with separate markup and JS (`public/js/import.js`, not `recipe-form.js`) and are **not** touched by this plan — imported recipes can still save with blank Prep/Cook time after this change. Flagging this as a likely follow-up: once this ships, Import becomes the one remaining path that can bypass the new requirement, which the Developer may want to raise as a new ticket for the user to create (per this agent's read-only Jira role) rather than silently expanding REW-52's scope.
- **Applies to both "Save as draft" and "Publish".** The ticket doesn't call out drafts as exempt, and the existing required-field check for Title/Instructions already applies uniformly regardless of the `action` value in both `POST /recipes` and `POST /recipes/:id/update`. Assuming the same uniform treatment for Prep/Total Time (i.e., a draft cannot be saved blank either) for consistency with that existing pattern. If product actually wants drafts to be exempt from required fields (a common pattern elsewhere), that's a different, narrower change — flagging in case the user wants to correct this.
- **No new DB constraint (`NOT NULL`).** Not adding a `NOT NULL` constraint to `prep_time`/`cook_time` at the database level. Existing rows almost certainly contain `NULL`s for one or both columns (the columns have always been optional), so a `NOT NULL` migration would need a backfill strategy and would also break the Import flow (explicitly out of scope above), which can still legitimately insert blank values. Enforcement stays at the application layer only, matching how `title`/`instructions` are enforced today (those two *do* have `NOT NULL` in the schema, but that constraint predates this ticket and isn't something to retroactively add here without a backfill plan — flagging as a possible future defense-in-depth follow-up, not part of this ticket).
- **Server-side failure path doesn't preserve other field values (pre-existing gap, not newly introduced).** Today, if the existing Title/Instructions server check fails, the handler flashes an error and does a plain redirect to `GET /recipes/new` (or `GET /recipes/:id/edit`), which re-renders a fresh form — any other fields the user had already filled in are lost. Extending the same check to Prep/Total Time inherits this same limitation for the (uncommon) case where the server-side check is the one that fires — normal browser usage never hits it, because the new client-side validation (Task 3) blocks the form submission before a request is ever sent, so the user never leaves the page and never loses data in the common case. Rewriting the redirect flow to repopulate all fields is a larger refactor than this ticket calls for; flagging as a known limitation rather than silently expanding scope.
- **Label casing/wording.** Ticket examples show "Prep Time *" and "Total Time *" (title case). The current form labels are lower-case ("Prep time", "Cook time"); the recipe view pages (`views/recipes/view.ejs`, `views/recipes/public-view.ejs`) already use title case ("Prep Time", "Cook Time"). Assuming the form labels should be updated to title case to match both the ticket and the rest of the app.

## Database changes
None. No migration is needed — `prep_time` and `cook_time` already exist as nullable `TEXT` columns (`database/migrations/001_create_recipes_table.sql`), and this plan deliberately does not add a `NOT NULL` constraint (would require a backfill for existing rows and would break the out-of-scope Import flow) or a new `total_time` column (see the "Total Time" open question above for why). This is an application-layer (client + route handler) validation change only.

## Security considerations
- **Server-side enforcement is the actual security-relevant control.** The client-side JS check (Task 4) is a UX improvement only and can be trivially bypassed (disabled JS, direct `POST`/curl, modified DOM). The `src/routes/recipeRoutes.js` guard (Task 5) is what actually prevents a blank-time recipe from being persisted, and it follows the exact same trusted pattern already used for Title/Instructions on the same two routes — no new validation architecture introduced.
- **No change to auth surface.** Both `POST /recipes` and `POST /recipes/:id/update` are already behind `requireAuth`; this change adds no new unauthenticated code path.
- **No change to CSRF handling.** Both forms already submit the existing `_csrf` hidden field; no new form/endpoint is introduced.
- **Input handling unchanged.** `prepTime`/`cookTime` continue to be `.trim()`'d the same way as before; EJS `<%= %>` escaping on re-render (e.g. `value="<%= recipe.prep_time || '' %>"` in `edit.ejs`) is unchanged, so no new stored-XSS surface from this text-field validation change.
- **No change to file upload handling, rate limiting, or multer/sharp/file-type validation** — this ticket only touches two plain text fields.
- Reviewer note: confirm the new `aria-describedby`/`aria-invalid` attributes don't collide with any existing `id`s on the page (`prepTimeError`/`cookTimeError` are new and were checked against a repo-wide search — no existing elements use those `id`s today).
