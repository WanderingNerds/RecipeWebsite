## Summary
QA found that the Sign In page's "Need a new confirmation email? Resend it" link is too narrow a recovery affordance — a user who forgot their password has no way to reset it. This plan replaces that link with a "Forgot Password?" link that opens a new centralized account-recovery page (`/auth/forgot-password`). That page collects a single email address and offers two actions: request a password-reset email (new, built on Supabase Auth's built-in `resetPasswordForEmail` API) or resend the confirmation email (existing functionality, reusing the current `POST /auth/resend-confirmation` handler unchanged, just re-entered from the new page instead of its own dedicated page). A new `/auth/reset-password` route handles the incoming Supabase recovery-link click and lets the user set a new password, after which they're signed out of the recovery-granted session and sent to Sign In to log in with the new password. No new database tables/columns are needed — this is entirely built on Supabase Auth's existing password-recovery and OTP-verification APIs, following the same `token_hash`/`type` verification pattern the app already uses for email confirmation (`/auth/callback`).

## Open questions / assumptions
- **Fate of the standalone `/auth/resend-confirmation` page.** The ticket says resend functionality "should not be removed... it should be moved into/incorporated into the new Forgot Password flow," and the Expected Result frames Forgot Password as "the centralized account-recovery page for both." I'm reading this as: retire `views/auth/resend-confirmation.ejs` as its own destination and its `GET /auth/resend-confirmation` page, but **keep the `POST /auth/resend-confirmation` handler exactly as-is** (proven, tested logic, no need to duplicate it) and have the new Forgot Password page's "Resend Confirmation Email" button submit directly to that existing endpoint. `GET /auth/resend-confirmation` becomes a redirect to `/auth/forgot-password` (preserving any `?email=` query param) rather than a 404, in case anything external still links to it. If the intent was instead to keep the standalone resend page fully intact *in addition to* linking it from the new page, that's a smaller, lower-risk variant of this same plan — flagging so the Developer can confirm before removing the view file if there's any doubt.
- **Single shared email field with two actions, not two separate pages.** The ticket's wording ("allow a user to enter their email address and choose the appropriate recovery action") reads as one form, one email field, two outcomes. I'm proposing a single `<form>` with one email `<input>` and two submit buttons using the HTML `formaction` attribute (well-supported in all evergreen browsers, no JavaScript required) so each button posts to a different endpoint (`/auth/forgot-password` for reset, `/auth/resend-confirmation` for resend) without duplicating the email field or adding client-side JS. This matches the codebase's existing convention of plain server-rendered forms with no auth-page JS. If the Developer or reviewer prefers two visually distinct sections/forms instead of two buttons in one form, that's a presentation-only variation on the same plan.
- **Post-reset session behavior (feeds AC9).** AC9 says "After successfully resetting their password, the user can sign in using the new password" — read literally, this implies the user ends up back at Sign In and logs in fresh, not auto-logged-in via the recovery session. I'm assuming the app should clear the recovery-granted session cookies immediately after `updateUser({ password })` succeeds and redirect to `/auth/login` with a success flash, rather than dropping the user straight into `/dashboard`. This is also the safer choice on a shared/public device. Flagging in case product actually wants auto-login after reset instead — that would just mean skipping the `clearAuthCookies` call and redirecting to `/dashboard` instead of `/auth/login`.
- **Supabase Dashboard configuration is out of code scope but required.** `resetPasswordForEmail`'s `redirectTo` URL (`{APP_URL}/auth/reset-password`) must be added to Supabase's allow-listed Redirect URLs (Settings > Authentication > URL Configuration) the same way `{APP_URL}/auth/callback` already is (per `docs/confluence/REW-41-email-confirmation-fix.md`). This is a one-time dashboard/infra change, not something committed in this repo — flagging it prominently so it isn't missed during review/deployment, since without it Supabase will reject or silently fall back on the redirect and the reset link will send the user to the wrong place.
- **Password policy reuse.** I'm assuming the new "set a new password" form reuses the exact same client/server validation already used at registration (`password.length < 8` in `POST /auth/register`), for consistency, rather than inventing a different policy. If Supabase's project-level password policy (configured in the dashboard, not visible in this repo) is stricter, its own rejection message from `updateUser()` should be surfaced to the user (this one case is not enumeration-sensitive, since the user has already proven access to the account by clicking the emailed link and reaching an authenticated recovery session).
- **No dedicated rate limiting on the two new email-triggering endpoints.** Neither `/auth/resend-confirmation` nor the new `/auth/forgot-password` reset-request endpoint has route-specific rate limiting today — only the app-wide general limiter (production-only, 100 req/15 min per IP, `src/app.js`) applies. This is a pre-existing gap for resend-confirmation, not one newly introduced here, but adding a second email-sending, enumeration-sensitive endpoint doubles the surface. Flagging as a recommended follow-up (possibly its own ticket) rather than silently expanding this ticket's scope.

## Security considerations
- **Email enumeration.** Both the new password-reset request and the existing resend-confirmation request must return the same generic, non-committal flash message regardless of whether the email exists or Supabase returns an error — this already matches the existing `POST /resend-confirmation` pattern and must be preserved for `POST /auth/forgot-password`, not weakened.
- **OTP type validation stays route-scoped.** `GET /auth/reset-password` must independently check `type === "recovery"` and must **not** be folded into `ALLOWED_OTP_TYPES` (which gates `/auth/callback` and should keep only accepting `signup`/`email`). A recovery-type token must never be able to log a user straight into `/dashboard` via `/auth/callback` — it must always land on the "set a new password" form.
- **Session-mutation / concurrency caveat (pre-existing pattern, worth flagging, not newly introduced).** `authMiddleware.js`'s `refreshSession()` call and `authRoutes.js`'s existing `verifyOtp()` call in `GET /auth/callback` both operate on the shared, module-level `supabase` singleton client, which internally mutates that client's current session — under concurrent requests on a long-lived server process this is a theoretical cross-request session-bleed risk that already exists in the codebase today. This ticket's `POST /auth/reset-password` needs its own `setSession` + `updateUser()` call; it should use a **freshly created Supabase client instance per request** (not the shared singleton) to avoid *adding to* that risk, even though fully fixing the pre-existing instances of this pattern is out of scope here — worth a one-line callout to the reviewer.
- **CSRF is currently disabled app-wide.** `src/app.js` has `doubleCsrfProtection` commented out (`// TEMPORARILY DISABLED ... TODO: Re-enable CSRF protection after debugging library issues`) and the `_csrf` hidden inputs on every form currently submit against an always-empty token. The two new forms in this ticket should still include the `_csrf` hidden field for consistency with every other form in the app (so re-enabling CSRF later doesn't require touching these views again), but reviewers should be aware this ticket is adding two more unauthenticated, state-changing POST endpoints to an app where CSRF protection is presently a no-op — not a regression caused by this ticket, but worth surfacing given the increased surface.
- **Rate limiting.** No route-specific limiter exists on `/auth/resend-confirmation` today, and this ticket adds a second email-triggering, enumeration-sensitive endpoint (`/auth/forgot-password`). Only the app-wide production-only general limiter (100 req/15 min/IP) applies. Flagging as a recommended follow-up ticket rather than expanding this one.
- **Password validation.** Reuses the existing `password.length < 8` / match-confirmation rule from registration for consistency; Supabase's own `updateUser()` error (if the project enforces a stricter policy) should be surfaced directly to the user on this authenticated path (not suppressed the way enumeration-sensitive errors are).
- **Post-reset session handling.** The recovery-granted session should be explicitly cleared (`clearAuthCookies`) after a successful password update, per AC9's implication that the user then signs in fresh — see Open Questions if that reading is wrong.
- **No changes to file upload, multer/sharp/file-type handling, or CORS** — out of scope for this ticket.
