## Summary

`+ Cookbook` renders on every My Favorites card, including recipes the viewer does not own, but clicking it for someone else's recipe fails with a generic `404 Recipe not found` (surfaced as an error toast by `toggleCookbookMembership`). Two layers enforce own-recipes-only and both have to move together: the application check in `handleCookbookRecipeAdd` (`src/routes/cookbookApiRoutes.js`), and the `cookbook_recipes` INSERT policy created by `database/migrations/010_create_cookbook_recipes_table.sql`. This change widens the **recipe** half of both checks to "the caller's own recipe (any status) **or** anyone's `status = 'published'` recipe" and leaves the **cookbook-ownership** half of both exactly as it is. Migration `012_create_meal_plan_recipes_table.sql` is the in-repo precedent — `+ Meal Plan` has always worked this way. Because migration `010` documents own-recipes-only as a deliberate database-layer guarantee, this is a knowing relaxation of a stated rule and needs explicit reviewer attention.

Nothing about the endpoint's security posture changes. `requireApiAuth`, route-level `csrfProtection` ahead of the rate limiter, `cookbookApiLimiter`, both UUID guards, the cookbook-owner lookup, the duplicate-safe `ignoreDuplicates` upsert and the response shape all stay byte-for-byte as they are.

Do not fall back to "Favorite this recipe" (it would be a live-looking control that cannot work) and do not hide the heart (it would shift the header row layout between cards).

2. **The REW-88 follow-up's reachability claim is wrong, and the fix is still worth making.** The Jira comment says the draft-heart branch "becomes reachable the moment REW-100 widens that policy". Reading the code, it does not become reachable through any UI path: another user's `draft` recipe row is invisible under RLS (migration `001` allows SELECT on own rows or `status = 'published'` only, and nothing since has widened that), `getCookbookRecipes` in `src/routes/cookbookRoutes.js` drops any junction row whose embedded `recipes` came back null, and `GET /recipes/liked` filters `.eq("status", "published")` on a public client. Assumption: make the fix anyway — it is one flag, it is correct defence in depth, and it is cheap to lock down with a render test. Do **not** write an acceptance step that asks QA to reach it in a browser.

3. **New edge case this ticket creates; no clean answer in the ticket.** Once a cookbook can hold someone else's recipe, that recipe's author can later flip it Private. The membership row survives (the same known gap already documented in `database/README.md` for `recipe_likes` and `meal_plan_recipes`), the recipe silently disappears from `/cookbooks/:id` because its embed is RLS-hidden, but `getCookbookRecipeCounts` counts `cookbook_recipes` rows without any recipe-visibility check — so `/cookbooks` can advertise "3 recipes" where the detail page renders 2. Assumption: accept and document for this ticket (matching how the analogous `recipe_likes` gap was handled). **Recommend the Developer file a follow-up Jira ticket for the count mismatch** — Planner does not create tickets.

4. **The two form-based cookbook add routes stay own-recipes-only (deliberate, not an oversight).** `POST /cookbooks/:id/recipes/:recipeId` and `POST /cookbooks/:id/add-recipes` in `src/routes/cookbookRoutes.js` keep their `.eq("user_id", req.user.id)` recipe filters. Their only UI entry points are owner-gated: the "Save to Cookbook(s)" widget sits inside `<% if (isOwner) { %>` in `views/recipes/view.ejs`, and the bulk picker lists only the caller's own recipes. An application check narrower than RLS is always safe. What must change there is prose only: two comments claim RLS also enforces recipe ownership, and that stops being true the moment `021` is applied.

5. **Migration number verified, not assumed.** `database/migrations/` currently tops out at `020_add_meal_plan_sharing.sql`, so `021` is the next free number. (Note the historical duplicate `003_` prefix; every file from `004` on is unique.)

## Database changes

**Yes — one new migration, `database/migrations/021_allow_published_recipes_in_cookbooks.sql`.** Described in prose; the Developer writes the SQL.

- **What changes:** exactly one policy — the `cookbook_recipes` INSERT policy created by `010`. Its `WITH CHECK` keeps requiring, unchanged, that the target cookbook belongs to `auth.uid()`. Its second requirement, that the referenced recipe belongs to `auth.uid()`, widens to "belongs to `auth.uid()` **or** has `status = 'published'`" — the identical shape migration `012` already uses for `meal_plan_recipes`. Drop-and-recreate, guarded so the file is re-runnable.
- **What does not change:** `010`'s SELECT and DELETE policies (both still scoped to cookbooks owned by `auth.uid()`, so a recipe author still cannot read or remove anything inside someone else's cookbook); both REW-19 public SELECT policies from `019`; every policy, grant and column on `recipes`; every index; every `ON DELETE CASCADE`. No table, column, index, grant, function or trigger is created or altered.
- **RLS implications.** After this, the database no longer prevents any published recipe from entering any cookbook whose owner asks for it. Two consequences the Reviewer should weigh deliberately: (a) the own-recipes-only behavior of the two form routes in `cookbookRoutes.js` becomes application-enforced only — acceptable, since narrower-than-RLS is always safe, and their comments are being corrected to say so; (b) a cookbook is now a genuinely mixed-ownership collection, which the card partial already handles per-card. Draft privacy is unaffected: another user's draft is still rejected by the widened `WITH CHECK`, and still invisible to SELECT under `001`.
- **Sharing is unaffected.** `019`'s public junction policy already requires the embedded recipe to be `status = 'published'`, and `/c/:id` reads through the anon key with an explicit published predicate on top — so a shared cookbook containing someone else's Public recipe renders, and that recipe drops out of the public view the moment its author makes it Private.
- **Deployment.** Apply manually in the Supabase SQL editor after `020`. No backfill, no environment variable, no package, no Vercel configuration change. **Will not be applied on this run** (QA excluded), so the branch ships with the migration file and automated coverage only.
- **Rollback.** Recreate `010`'s own-recipes-only `WITH CHECK`. No data is lost: any non-owned membership rows inserted in the meantime remain, remain visible to the cookbook owner, and remain removable by them; only new non-owned inserts stop being possible.

## Security considerations

- **This is a knowing relaxation of a documented database-layer guarantee.** Migration `010` states in its header that a user "cannot add someone else's recipe (including another user's published recipe) into their own cookbook even if application code were buggy." That sentence stops being true. Reviewer must confirm the recreated policy still `AND`s cookbook ownership and widened **only** the recipe clause — an `OR` in the wrong place would let a user insert into a cookbook they do not own.
- **Auth, CSRF and rate limiting are a hard boundary and are untouched.** `POST /api/cookbooks/:id/recipes/:recipeId` keeps `requireApiAuth` first, then `csrfProtection` (route-level, because the global `csrfProtectionExceptMultipart` skips multipart bodies), then `cookbookApiLimiter` (30/min keyed on user id), then the handler. CSRF must stay ahead of the limiter so a forged cross-site request cannot burn the victim's quota. The existing layer-order test enforces all of this and must pass unmodified — it must not be loosened to accommodate the implementation.
- **Input validation unchanged.** Both UUID guards stay ahead of every query, so a malformed cookbook or recipe id still returns `400` without opening a connection. The existing malformed-id tests cover path traversal and SQL-injection-shaped inputs and must keep passing.
- **Uniform, non-probing error responses.** Non-owned cookbook, nonexistent cookbook, nonexistent recipe, another user's draft recipe and a failed lookup must all keep their current generic messages and status codes. Do not add a "this recipe is private" message or a `403` — that would turn the endpoint into an existence oracle for other users' draft recipe ids.
- **Draft privacy is the line that must not move.** Another user's draft recipe must remain rejected at both layers, and the application predicate must stay explicit rather than trusting the `recipes` SELECT policy, so the two layers keep failing independently.
- **No status claim to a non-owner**, which is the point of the heart fix. `recipes.user_id` remains fetched for presentation only and never rendered, and it is never the authorization check — `/recipes/:id/edit`, `/:id/update` and `/:id/delete` each enforce ownership themselves.
- **Author cannot reach into someone else's cookbook.** `cookbook_recipes` SELECT and DELETE remain cookbook-owner-scoped, and `DELETE /api/cookbooks/:id/recipes/:recipeId` keeps its `getOwnedCookbook` gate. Adding your recipe to nobody — and having someone add it — grants no new capability to either party.
- **No new endpoint, no new client-side request, no new inline script, no CSP change, no new dependency, no file-upload surface touched.**
