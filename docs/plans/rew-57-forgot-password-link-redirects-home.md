## Summary
The REW-54 forgot-password flow ships a server-side handler, `GET /auth/reset-password`, that only understands `?token_hash=...&type=recovery` query parameters. But the "Reset Password" email template applied to the Supabase Dashboard in REW-42 (`docs/email-templates/reset-password.html`) links to `{{ .ConfirmationURL }}`, i.e. Supabase's own `/auth/v1/verify?token=...&type=recovery&redirect_to=...` endpoint. Supabase verifies that token itself and then 302s the browser to `redirect_to` with the session in a **URL hash fragment** (`#access_token=...&refresh_token=...&type=recovery`, implicit flow) — and if `redirect_to` is not on the project's Redirect URL allow-list (which is the case whenever `APP_URL` is unset on Vercel, because the code then sends `http://localhost:3000/auth/reset-password`, or when `/auth/reset-password` was never added to the allow-list as REW-54 required), Supabase falls back to the **Site URL**, which is the Home page. Fragments are never sent to the server, so Express simply renders `/`. This plan (a) documents the manual Supabase/Vercel configuration that must be corrected, (b) changes the email template so the link carries `token_hash` directly to `/auth/reset-password` (the flow the code was written for), and (c) hardens the in-repo code so that the flow still completes — and never dead-ends on Home — even when the template or allow-list is misconfigured: a fragment-to-cookie bridge for implicit-flow links, a Home-route guard for email-link query parameters, inline invalid/expired error states with a "request a new link" action, and a single `getAppUrl()` helper that stops silently emitting `localhost` redirect URLs in production.

## Root cause analysis (for the Developer and Reviewer)
Evidence gathered from the repo:

1. **Email template mismatch (primary code-level cause).** `docs/email-templates/reset-password.html` lines 60 and 71 use `{{ .ConfirmationURL }}`. For a recovery email that URL points at `https://<project>.supabase.co/auth/v1/verify?token=<token>&type=recovery&redirect_to=<redirectTo>`. GoTrue consumes the token and redirects the browser to `redirect_to` with tokens in the `#` fragment. The app's `GET /auth/reset-password` (`src/routes/authRoutes.js` lines 282-327) reads `req.query.token_hash`, which is only populated when the template is customised to `...?token_hash={{ .TokenHash }}&type=recovery` (the format Supabase documents for server-side verification and the format `docs/api/email-confirmation.md` line 47 *assumed* the emails would have). The template was never updated for that.
2. **`redirect_to` falls back to Site URL → Home (the exact reported symptom).** `.env` defines only `NODE_ENV`, `PORT`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SESSION_SECRET` — there is no `APP_URL`, and the REW-41 Confluence deployment checklist item "Set `APP_URL` environment variable in Vercel" is unchecked. `POST /auth/forgot-password` (line 204) therefore sends `redirectTo = http://localhost:3000/auth/reset-password` in production, which cannot be on the production allow-list, so Supabase redirects to the Site URL (the Home page) with `#access_token=...&type=recovery`. The same happens if `APP_URL` is correct but `https://<domain>/auth/reset-password` was never added to *Authentication > URL Configuration > Redirect URLs* (a manual step REW-54 flagged but which cannot be verified from the repo).
3. **Even with a correct allow-list the flow still fails.** The browser would land on `/auth/reset-password#access_token=...` with no query string; the handler flashes "invalid or expired" and redirects to `/auth/forgot-password`. Nothing in the app reads `window.location.hash` (checked `public/js/*.js`, `views/**`), and `src/config/supabase.js` uses the default implicit flow (no `flowType`); PKCE (`?code=`) is not an option for a stateless server-side Express/Vercel app because the code verifier lives in the client that initiated the request.
4. **Second path to Home.** `GET /auth/forgot-password` is wrapped in `redirectIfAuthenticated`, which redirects to `/`. If the browser still holds `sb-access-token`/`sb-refresh-token` cookies (e.g. from an earlier reset-link click whose form was abandoned — `GET /auth/reset-password` sets 1h/7d cookies before the user submits anything), every failure branch in `GET /auth/reset-password` and `POST /auth/reset-password` that redirects to `/auth/forgot-password` bounces the user to Home.
5. **`vercel.json` is very unlikely to be the cause.** It contains only a `functions` block; the recent "Fixed vercel.json" commits show routing was suspected and rewrites were tried and removed. If `/auth/login` and `/auth/forgot-password` render in production (the ticket's steps 1-3 succeed), Express routing on Vercel works and `/auth/reset-password` resolves too. A diagnostic AC below confirms this; do not touch `vercel.json` unless that diagnostic fails.
6. **Latent sibling bug (out of scope, needs its own ticket):** `docs/email-templates/confirm-signup.html` also uses `{{ .ConfirmationURL }}`, so `/auth/callback` has the identical mismatch for signup confirmation. Not addressed here beyond the Home-route guard and generic fragment forwarding, which happen to help it.

## Open questions / assumptions
- **Is `APP_URL` set in the Vercel Production environment?** Unknown from the repo. Assumption: treat as possibly unset; Task 1 verifies and Task 3 stops the silent `localhost` fallback in production either way.
- **Which Reset Password template is live in the Supabase Dashboard?** Assumption: the REW-42 branded template with `{{ .ConfirmationURL }}`. Task 1 confirms; Task 2 changes the repo copy and Task 1 applies it.
- **Template link base: `{{ .SiteURL }}` vs `{{ .RedirectTo }}`.** Recommendation: `{{ .SiteURL }}/auth/reset-password?token_hash={{ .TokenHash }}&type=recovery`. It is independent of both `APP_URL` and the Redirect-URL allow-list, so the link can never land on Home. Trade-off: emails triggered from a local dev server will point at the production origin (Site URL); developers testing locally must paste the `token_hash` into a `localhost` URL. If the team prefers per-environment links, `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=recovery` works too and, if `redirect_to` is not allow-listed, degrades to the Site URL root with the query intact — which the new Home-route guard (Task 5) forwards correctly. Either way the code in this plan handles both.
- **Scope of the fragment bridge (Tasks 4c, 6).** Strictly, fixing the template + configuration makes the existing server-side path work with no JS. The bridge is defence-in-depth so the flow also completes with the default `{{ .ConfirmationURL }}` template and survives allow-list mistakes — justified because the failing piece (dashboard config) is outside the repo, has already been missed once, and the ticket is High priority with an AC of "reset links do not redirect to the Home page". If the team wants the minimal fix only, drop Tasks 4c and 6 and keep everything else; the plan is written so those two are separable.
- **Client-side JS on an auth page.** The codebase has no auth-page JS today, but CSP (`scriptSrc: 'self'`) permits same-origin external scripts and the layout already loads four. Assumption: one small new file `public/js/auth-recovery.js` is acceptable. No inline scripts (CSP would block them).
- **Password policy.** Keep the existing rule (min 8 chars, must match) used by `POST /auth/register` and `POST /auth/reset-password`; surface Supabase's own `updateUser` rejection message if the project's dashboard password policy is stricter. No new policy.
- **Post-reset behaviour.** Keep REW-54's decision: clear the recovery session and send the user to `/auth/login` with a success flash. Matches the ticket's "direct the user to sign in using their new password".
- **`redirectIfAuthenticated` stays untouched.** Auth middleware is a hard boundary. The Home bounce (root cause 4) is closed by clearing recovery cookies on failure paths and by rendering error states inline instead of redirecting to `/auth/forgot-password`.

## Security considerations
- **Fragment bridge is the highest-risk new surface.** It turns browser-supplied tokens into httpOnly cookies. Mandatory controls: `type` must be `recovery`; `access_token` must be validated by `supabase.auth.getUser` before any cookie is set; the pair is only ever stored as cookies, never logged, never rendered; same-origin `Origin`/`Referer` check against `getAppUrl()` (mitigates login-CSRF/session-injection while global CSRF is disabled — this is an added check, not a change to security middleware); recommended `amr` contains `recovery` check so a normal session JWT cannot be used to reach the password-change form without a recovery link (which would otherwise reduce the `recovery-session` marker to "any valid token"). Reviewer should confirm none of these are skipped.
- **Tokens in the URL fragment** are visible to browser history and any script on the page. The script must `history.replaceState` to strip the fragment immediately after reading it; CSP `scriptSrc 'self'` already blocks third-party scripts.
- **No open redirects.** The Home-route guard and the script only ever navigate to fixed internal paths (`/auth/reset-password`, `/auth/callback`) and forward a whitelisted set of parameters; `error_code` is constrained to a safe character class and mapped to fixed copy — `error_description` from Supabase is never rendered.
- **Cookie hygiene.** Every failure path in the recovery flow clears `sb-access-token`, `sb-refresh-token`, and `recovery-session`, so an abandoned recovery attempt cannot leave a browser "logged in" or trigger `redirectIfAuthenticated` bounces. `redirectIfAuthenticated`, `requireAuth`, `optionalAuth` are not modified.
- **`getAppUrl()` must never trust `Host`/`X-Forwarded-Host`.** Email links are built from it; a header-injected origin would send password-reset links to an attacker-controlled host.
- **Email enumeration** behaviour of `POST /auth/forgot-password` is unchanged (same generic message on every outcome).
- **CSRF** remains globally disabled in `src/app.js` (pre-existing, out of scope). New forms/requests still carry `_csrf` for when it is re-enabled.
- **Rate limiting.** Only the production-wide limiter applies. The bridge endpoint does a Supabase `getUser` call per request; a route-specific limiter is recommended as a follow-up ticket rather than expanding this fix.
- **Error messages** stay generic ("invalid or expired") and do not distinguish "token never existed" from "token expired" beyond the mapped `otp_expired` case, which Supabase already reveals in the redirect.
- No file-upload, CORS, or helmet changes.
