## Summary

`/recipes/liked` ("My Favorites") still renders the old lightweight `views/partials/recipe-card.ejs`: a bare `10 minutes` / `4 servings` metadata line, an `@author` handle, at most two category chips, no tags, no heart, no Cookbook, no Edit/Delete, no Share. REW-86 already built the standardized card in `views/partials/recipe-summary-card.ejs` and every REW-87 requirement except one exists there. The work is therefore **not** a new card — it is teaching the shared partial a third surface and pointing Favorites at it.

The one structural difference from REW-86: My Recipes is uniformly *owned* by the viewer, and Browse is uniformly *not actionable*. My Favorites is **mixed** — mostly other people's Public recipes, sometimes the viewer's own. The partial's current `isPublic` boolean encodes "public surface" and "owner surface" as the same axis, so REW-87 must split that into per-card ownership (`Edit`/`Delete` only when `recipe.user_id === user.id`) while leaving Browse and My Recipes output unchanged. The route at `src/routes/index.js` also has to start fetching the data the standardized card needs — tags, categories, `user_id`, `status` — which it does not fetch today.

## Open questions / assumptions

1. **`+ Cookbook` on a recipe you do not own does not currently work, at two layers.** This is the one genuine blocker in the ticket.
   - `POST /api/cookbooks/:id/recipes/:recipeId` (`src/routes/cookbookApiRoutes.js`, ~lines 197–210) explicitly re-checks the recipe with `.eq("user_id", req.user.id)` and returns `404 Recipe not found` otherwise. The comment there says own-recipes-only "is the correct rule for the My Recipes surface this powers".
   - Underneath it, the RLS INSERT policy in `database/migrations/010_create_cookbook_recipes_table.sql` enforces the same thing at the database layer, deliberately: *"A user cannot add someone else's recipe (including another user's published recipe) into their own cookbook even if application code were buggy."*
   - **Assumption (needs user sign-off before Task 5 is written):** REW-87 widens this to **own OR published**, matching what `database/migrations/012_create_meal_plan_recipes_table.sql` already allows for meal plans (`recipes.user_id = auth.uid() OR recipes.status = 'published'`). Rationale: meal plans are the outlier-free precedent; the public-cookbook read policy added in `019_add_cookbook_sharing.sql` already filters embedded recipes to `status = 'published'`, so a shared cookbook cannot leak a recipe that later goes Private; and REW-84 already established that a user may act on other people's Public recipes.
   - **Knock-on, must be verified, not assumed:** `views/cookbooks/view.ejs` today assumes every recipe in a cookbook is the viewer's. It links titles to `/recipes/:id` (fine — that route serves own *or* published) and shows a `Private`/`Public` status pill (misleading for someone else's recipe). It does **not** render Edit/Delete there, so nothing leaks. REW-88 owns cleaning that card up; REW-87 should not rewrite it, but QA must confirm a cookbook containing another user's recipe renders and reads correctly.
   - **Fallback if the user rejects the widening:** show `+ Cookbook` only on favorites the viewer owns, and say so explicitly in the ticket. That contradicts the written acceptance criterion, so it needs the user's decision, not the Developer's.
2. **Where the title links.** Browse links to `/r/:id`, My Recipes to `/recipes/:id`. **Assumption:** Favorites links to `/recipes/:id`. `/recipes/liked` is behind `requireAuth`, `GET /recipes/:id` already serves any recipe RLS allows (own or published) and computes `isOwner` itself, and it is the richer authenticated view (scaling, favorite, cookbook widget). This changes today's behavior, which links to `/r/:id`.
3. **No visibility toggle on Favorites.** The ticket's requirement list omits it, and every recipe reachable from this page is already Public (the route filters `status = 'published'`). **Assumption:** the favorites surface renders neither the REW-86 Private/Public control nor Browse's read-only status pill — a "Public" pill on every card is pure noise. Owner-only Edit/Delete still appear; owners who want to flip visibility do it from My Recipes.
4. **Unfavoriting does not remove the card.** `public/js/likes.js` is optimistic and offers a 5-second Undo toast; yanking the card out from under that toast would break undo. **Assumption:** the heart flips to the unfavorited state, the card stays until the next load, and it is gone after a refresh. QA should treat that as correct, not a bug.
5. **Category and tag chips are not links on this surface.** On My Recipes they link to `/recipes?category=…` / `?tags=…`, which filters *your own* recipes — following one from a favorited stranger's recipe would land on an unrelated (often empty) list. **Assumption:** render them as static `<span>`s here, exactly as the Browse branch already does.
6. **`Adapted from` attribution.** The partial hides `original_author` on the Browse branch. Both detail views (`views/recipes/view.ejs`, `views/recipes/public-view.ejs`) show it to every viewer. **Assumption:** show it on the favorites card when present, and add `original_author` to the route's column list.
7. **Page heading still says "Liked Recipes".** REW-66 replaced this terminology with "Favorites" and the dashboard entry point is labelled "My Favorites", but `views/recipes/liked.ejs` was missed. **Assumption:** rename the `<h1>`, the route's `title`, and the empty-state copy to "My Favorites" / favorites wording as part of this ticket, since the ticket is literally named for the surface. It touches one assertion in `src/views/recipeCard.test.js`. If the user prefers strict scope, drop Task 8 — nothing else depends on it. The URL `/recipes/liked` stays as-is either way (renaming it would break the dashboard card, the navbar tests, and any bookmark).
8. **Deleting from Favorites lands on My Recipes.** `POST /recipes/:id/delete` hard-codes `res.redirect("/recipes")`. **Assumption:** leave it. Adding a return-path parameter introduces a redirect-target input surface for one page's convenience; the flash message still confirms the delete. Call it out to QA rather than "fixing" it.
9. **No pagination on Favorites.** The route fetches every liked recipe in one unbounded `.in("id", …)`. Pre-existing; the richer card makes a long page heavier but not broken. Out of scope — flag if the user wants it ticketed.

## Database changes

**No migration is required for Tasks 1–4, 6, 7, or 8.** Everything the standardized favorites card reads is already permitted:

- `recipes` — `001_create_recipes_table.sql` grants SELECT on any row with `status = 'published'`, all columns, including `user_id`. Fetching `user_id` to decide whether to draw Edit/Delete needs no policy change.
- `recipe_categories` / `recipe_tags` — `013_public_recipe_card_metadata.sql` already allows anyone to read category and tag links for published recipes. This is exactly what Browse relies on.
- Favorite toggling, `+ Meal Plan`, Edit, and Delete all reuse existing policies unchanged. Meal plans in particular already accept another user's published recipe (`012_create_meal_plan_recipes_table.sql`).

**One migration is required if Open Question 1 is resolved in favor of widening:** `database/migrations/021_allow_public_recipes_in_cookbooks.sql`, replacing the `"Users can insert own cookbook recipes"` INSERT policy on `cookbook_recipes` so the recipe half of the check passes for a recipe the caller owns **or** a recipe with `status = 'published'`. The cookbook-ownership half of the check is unchanged — a user still cannot add to someone else's cookbook. SELECT and DELETE policies are untouched. `021` is the next free number (`020` is the highest applied); never edit an applied migration. This is a deliberate relaxation of a rule migration 010 documents as intentional, so it needs an explicit note in the migration header and explicit Reviewer attention.

## Security considerations

- **Ownership is decided server-side and is presentational only on the card.** `isOwner` gates whether Edit/Delete are *drawn*. The actual protection is unchanged and must stay: `POST /recipes/:id/delete` filters `.eq("user_id", req.user.id)` on top of the owner-only RLS DELETE policy, and `GET /recipes/:id/edit` + `POST /:id/update` enforce ownership independently. Never let the card's flag become the only check.
- **Do not render `user_id` into the HTML.** It is fetched solely to compute `isOwner`. Assert its absence in the view tests.
- **Owner controls must not leak across surfaces.** After the Task 1 refactor, re-confirm that `surface: 'browse'` still renders no Edit, Delete, Share, `+ Cookbook`, heart, or visibility toggle — *including when the signed-in viewer owns the recipe*. The existing REW-86 test `'REW-86 owner-only controls never leak onto the public Browse card'` covers this; it must keep passing unmodified.
- **The favorites list must stay published-only.** Do not drop `.eq("status", "published")` from the route. If a favorited recipe is later made Private it should vanish from this page, not render with an owner's private data visible to a stranger who once favorited it.
- **CSRF.** The Delete form keeps its hidden `_csrf` field. **Finding to flag, not silently fix:** `POST /recipes/:id/delete` (`src/routes/recipeRoutes.js` line 972) relies only on the global `csrfProtectionExceptMultipart`, which by design skips validation for `multipart/form-data` bodies — the exact hole that `POST /:id/visibility` and `POST /:id/clone` each re-apply route-level `csrfProtection` to close (see the comment at recipeRoutes.js lines 958–966). Delete never got the same treatment. REW-87 now puts a Delete button on a second page, so Reviewer should see this. Recommend a separate ticket rather than folding a security fix into a card-layout ticket; Developer to create it.
- **RLS widening (if Task 5 lands) is the highest-risk change in this ticket.** Verify by hand, not by assumption: a user still cannot add to a cookbook they do not own; a user still cannot add another user's **draft** recipe; a shared/public cookbook containing another user's published recipe still renders (the `019_add_cookbook_sharing.sql` read policy already filters to `status = 'published'`, so a later flip to Private removes it from the public view); and `cookbook_recipes` DELETE remains cookbook-owner-scoped, so a recipe author cannot reach into someone else's cookbook.
- **Rate limiting.** No new endpoints in Tasks 1–4. The cookbook and meal-plan APIs keep their existing per-user limiters and `requireApiAuth`; do not weaken them when relaxing the recipe lookup.
- **CSRF on JSON actions.** `+ Meal Plan` and `+ Cookbook` go through the `window.fetch` wrapper in `public/js/main.js` that injects `x-csrf-token`. Do not bypass it, and do not add inline scripts — helmet's CSP is `scriptSrc: ['self']`.
- **Escaping.** Titles, authors, `original_author`, and tag names are user-controlled and come from *other* users on this surface. Every field stays on `<%= %>`. The existing `<script>alert(1)</script>` fixture in `src/views/recipeCard.test.js` should be exercised through the favorites branch too.
- **Share leaks nothing.** Same inert `disabled` / `aria-disabled` placeholder as REW-86, with no `href` and no target URL.
- **Favorite endpoint is unchanged.** `/api/likes/:id` already enforces `status = 'published'` and auth server-side; the card only calls it.

## Acceptance criteria

- [ ] A My Favorites card for a recipe the viewer does **not** own shows: thumbnail (when present), clickable title, favorite heart, author, tags, `Prep Time:`, `Cook Time:`, `Servings:`, `Difficulty:`, `+ Meal Plan`, `+ Cookbook`, and Share — and shows **no** Edit and **no** Delete.
- [ ] A My Favorites card for a recipe the viewer **does** own shows all of the above **plus** Edit and Delete.
- [ ] Neither favorites card shows a Private/Public toggle or a Public/Private status pill.
- [ ] Clicking a card title opens that recipe's full view and the page loads for both owned and non-owned favorites.
- [ ] Prep time, cook time, servings, and difficulty render as `Label: value` and match, character for character, the labels shown for the same recipe on a Browse card.
- [ ] A recipe missing prep time, cook time, servings, difficulty, tags, categories, author, or thumbnail renders no stray label, no empty chip row, and no `undefined`/`null` text.
- [ ] Clicking the heart on a favorites card unfavorites the recipe without a full-page navigation, shows the Undo toast, and the card remains on the page until reload; after reload the recipe is gone from My Favorites.
- [ ] Using Undo within the toast window re-favorites the recipe, and it is still present after a reload.
- [ ] Author and tags are visible on the card; tags are the recipe's own tags, not truncated to two categories as before.
- [ ] Category and tag chips on this surface are plain text, not links to `/recipes?category=` / `?tags=`.
- [ ] `+ Meal Plan` opens the existing modal and successfully adds a favorited recipe the viewer does not own.
- [ ] `+ Cookbook` opens the existing modal and successfully adds a favorited recipe the viewer does not own; clicking twice is a no-op, not an error; the recipe then appears on that cookbook's page. *(Depends on Open Question 1 / Task 5.)*
- [ ] Adding another user's **draft** recipe to a cookbook is still rejected with a generic 404, via both the API and direct SQL under RLS. *(Only if Task 5 lands.)*
- [ ] Adding a recipe to a cookbook the caller does not own is still rejected. *(Only if Task 5 lands.)*
- [ ] Edit on an owned favorite opens `/recipes/:id/edit`; Delete prompts for confirmation, removes the recipe, and shows the success flash (landing on My Recipes is expected, see Open Question 8).
- [ ] A crafted `POST /recipes/:id/delete` for a recipe owned by someone else deletes nothing.
- [ ] The Share button is visible on every favorites card, is clearly inert, performs no navigation or request, and exposes no URL.
- [ ] Browse cards are unchanged: no Edit, Delete, heart, `+ Cookbook`, Share, or visibility toggle — including when the signed-in viewer owns the recipe being browsed.
- [ ] My Recipes cards are unchanged: title, heart, Private/Public toggle, author, tags, the four labels, `+ Meal Plan`, `+ Cookbook`, Edit, Delete, Share all still present and working.
- [ ] Search, public cookbook, and public meal-plan pages still render the old `recipe-card` partial unchanged.
- [ ] The rendered My Favorites HTML contains no recipe `user_id` value.
- [ ] The My Favorites page renders correctly with 0, 1, and many favorites; the empty state and its Browse Recipes call to action still appear at 0.
- [ ] A favorited recipe whose owner later makes it Private disappears from My Favorites and does not error.
- [ ] Card actions wrap rather than overflow at 375px width on both the owner and non-owner variants, and Delete is not adjacent enough to Edit to be mis-tapped.
- [ ] All controls are keyboard reachable with visible focus; the heart and any icon-only control have accessible labels.
- [ ] A favorited recipe titled `<script>alert(1)</script>` with a tag of the same shape renders escaped on the card.
- [ ] `npm test` passes, including the rewritten Liked Recipes view test and the new favorites owner/non-owner tests.
